# 从 TPC-C 失败报告反推数据库瓶颈

性能报告不是一个分数，而是一组观测。真正有效的调优从“把观测转成假设”开始。

## 四类常见信号

### 1. 超时

超时只说明端到端路径没有按时完成。需要进一步拆分：解析、优化、执行、锁等待、日志刷盘、索引访问和结果传输分别花了多少时间。

### 2. 语义失败

例如 FLOAT32 要求 0 ULP，意味着实现不能先提升为双精度、计算后再随意转换；并发情况下还必须避免旧版本覆盖新版本。它通常是类型系统与事务语义共同造成的问题。

### 3. Peak RSS

较低的 Peak RSS 可能说明内存利用高效，也可能说明系统没有使用足够大的缓冲池、缓存和批处理结构。指标本身没有方向，必须结合吞吐、缺页、磁盘 I/O 与 CPU 利用率解释。

### 4. 磁盘占用

过大的数据文件可能来自固定宽度记录、页内碎片、索引冗余、WAL 未回收或元数据重复。先测量每张表和每类页，再决定优化对象。

## 建议的 profiling 层次

1. 使用 benchmark 日志定位事务与阶段。
2. 用 `perf stat` 判断 CPU、分支、缓存和 page fault 特征。
3. 用 `perf record` 或火焰图定位热点调用路径。
4. 用数据库内部计数器验证锁等待、页命中与日志写入。
5. 最后才修改实现，并用同一测试复验。

调优不是“猜哪里慢”，而是不断缩小仍与全部证据相容的原因集合。
